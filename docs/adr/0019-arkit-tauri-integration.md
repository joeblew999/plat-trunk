# ADR-0019: ARKit Integration via Tauri v2

**Status:** Proposed  
**Date:** March 2026  
**Author:** Gerard Webb  
**Depends on:** ADR-0012 (deployment topologies), ADR-0020 (Tauri v2 native shell)  
**See also:** [0019-arkit-use-cases.md](0019-arkit-use-cases.md) — user-facing use case roadmap and research

---

## Context

plat-trunk runs as a browser-native CAD platform — Truck B-Rep kernel compiled to
WASM, deployed on Cloudflare Workers. Tauri v2 wraps that same frontend in a
native iOS/macOS shell (Tauri v2), giving access to platform APIs that are
unavailable or severely restricted inside a browser.

ARKit is the most immediately valuable of those APIs. It gives plat-trunk:

- Real-world measurement at millimetre precision
- Physical surface detection (floors, walls, benches, faces of objects)
- LiDAR depth scanning on supported devices (iPhone 12 Pro and later, iPad Pro)
- Stable AR anchors that persist across sessions
- Full camera access with pose tracking

**WebXR cannot replace this.** Safari's WebXR implementation has no LiDAR mesh
access, no RoomPlan, weak plane detection, and no anchor persistence. For any
serious spatial use case, native ARKit via Tauri is the only viable path on iOS.

---

## Decision

Add ARKit as a first-class input/output channel for plat-trunk, implemented as
a Tauri v2 Swift plugin living at `lib/arkit/`.

The plugin follows the `tauri-specta` pattern validated in
`lib/observe/demo-tauri/` — Rust commands are defined in `src-tauri/src/commands.rs`,
TypeScript bindings are auto-generated into `src/bindings.ts`, and the frontend
calls typed `commands.*` functions. Swift lives in `src-tauri/gen/apple/Sources/`.

All ARKit data crosses the IPC boundary as plain JSON or flat typed arrays.
The frontend receives events via Tauri's `emit` / `listen` mechanism — the same
pattern already used in the observe demo for streaming worker status updates.

---

## Why ARKit + Tauri over alternatives

| Option | Plane detection | LiDAR mesh | Anchor persistence | Ships today |
|--------|----------------|------------|-------------------|-------------|
| ARKit via Tauri v2 | ✓ excellent | ✓ iPhone Pro / iPad Pro | ✓ | ✓ |
| WebXR (Safari) | △ basic | ✗ | ✗ | ✓ |
| RealityKit alone | ✓ | ✓ | ✓ | requires full native rewrite |
| Vuforia / 8th Wall | ✓ | ✗ | △ | adds external dependency + cost |

Tauri v2 is already in the stack. The incremental cost of adding a Swift plugin
is low. This is not a new platform decision — it is extending a decision already made.

## Coordinate systems

ARKit uses a right-handed, Y-up world coordinate system in metres, with the
session origin at the device position when the session starts.

The Truck kernel uses a right-handed, Z-up system (standard mechanical CAD
convention). The bridge function `arkit_to_truck` handles this transform and
lives in `lib/arkit/src-tauri/src/transform.rs`. All coordinate data flowing
into `cadCommand()` has already been transformed before it reaches the WASM
frontend.

```
ARKit world (Y-up, metres)
    ↓  arkit_to_truck()   [lib/arkit/src-tauri/src/transform.rs]
Truck model space (Z-up, metres)
    ↓  existing pipeline
ECEF / Mercator / MVT tile space
```

## IPC event contract

Swift → Rust → TypeScript events follow a consistent envelope:

```typescript
// Emitted by Swift, received in TypeScript via listen('arkit:*')
type ArkitPlaneEvent = {
  id: string           // ARPlaneAnchor identifier
  transform: number[]  // 4x4 column-major, already in Truck Z-up space
  extent: [number, number, number]  // width, height, depth in metres
  alignment: 'horizontal' | 'vertical'
}

type ArkitMeasureEvent = {
  distance_m: number
  point_a: [number, number, number]  // Truck Z-up space
  point_b: [number, number, number]
}

type ArkitMeshEvent = {
  anchor_id: string
  vertices: Float32Array   // flat [x,y,z, x,y,z, ...]  Truck Z-up space
  faces: Uint32Array       // flat triangle indices
}
```

## Implementation phases

```
Phase 1 — no ARSession dependency (any iPhone, any iPad)
  UC-1  AR QuickLook preview
  UC-2  Object Capture photogrammetry

Phase 2 — active ARSession (plane detection, camera background)
  UC-3  AR measure → sketch dimension
  UC-4  Plane detection → set sketch plane
  UC-5  Place live model in AR world

Phase 3 — LiDAR devices only (iPhone 12 Pro+, iPad Pro 2020+)
  UC-6  LiDAR scan → reference mesh
  UC-7  RoomPlan → structured geometry
  UC-8  LiDAR mesh → FEA pipeline
```

Phase 2 requires `ARWorldTrackingConfiguration` running behind the WebView via
a custom `WKWebView` subclass rendering the camera feed as the window background.

Phase 3 requires `ARWorldTrackingConfiguration.sceneReconstruction = .mesh`.
Mesh anchor vertices are streamed incrementally as delta updates, not full re-sends.
RoomPlan walls map to `truck::Solid` boxes; doors/windows become Boolean subtracts.

UC-1 is the recommended starting point — minimal dependencies, no ARSession,
works on every device.

## Out of scope

- **Android AR** — ARCore is a separate decision. Not in this ADR.
- **visionOS / Apple Vision Pro** — separate ADR when hardware is accessible.
- **Multi-user shared AR** — deferred until CRDT sync (ADR-0001) is fully stable.
- **GPS-anchored AR at construction scale** — requires ARKit geo-anchors + mapping data. Separate ADR.
