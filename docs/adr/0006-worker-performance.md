# ADR-0006: Runtime Performance — Worker + Browser

- **Status:** Proposed
- **Date:** 2026-03-09
- **Related:** ADR-0004 (WASM Boundary Contracts), ADR-0001 (Multi-Actor Sync)

## Context

`systems/truck/worker/src/index.ts` has grown to 1,146 lines mixing 8 concerns into a single file. This causes measurable performance problems at runtime:

### Problem 1: Schema converted to Zod 3× at runtime (DRY violation)

`cad-schema.json` is a static build artifact (generated from Rust). Yet it gets converted to Zod schemas at runtime in three separate places:

| Where | When | What |
|-------|------|------|
| `mountModule()` line 413 | Module load (cold start) | Zod schemas for ~42 OpenAPI route bodies |
| `registerSchemaTools()` lines 756, 770 | Every `/mcp` request | Zod schemas for ~29 MCP tool inputs |
| `getMcpToolList()` lines 924-955 | Every `/llms-full.txt` and `/server-card.json` hit | JSON Schema tool catalog |

All three read the same static JSON and produce deterministic output. This is pure waste.

### Problem 2: MCP server rebuilt per request

`createMcpServer()` instantiates a new `McpServer` and registers all ~29 tools on every `/mcp` request. The tool definitions (names, descriptions, Zod schemas) are static — only the handler closures need runtime `env`.

### Problem 3: `executeServerDirect` replays ALL ops from scratch

Every MCP data-plane command (e.g. `cad_add_cube`) replays the entire op history through `HeadlessController`. The 10th cube replays all 10 ops. `replay.ts` already has R2-based caching with hash-based invalidation, but `executeServerDirect` doesn't use it.

### Problem 4: `gcModels()` runs on every API request

The middleware `gcModels()` iterates the entire `models` Map on every `/api/*` request, including SSE keepalives that fire every 100ms. It only needs to run once per minute.

### Problem 5: 1,146-line monolith

The file mixes: Zod schemas, session state, SSE event bus, server-direct execution, schema-driven route factory, model persistence routes, op-log routes, scene cache routes, MCP tool registration, discovery endpoints (llms.txt, robots.txt, agent.json, server-card.json), and SPA fallback. This makes all the above problems hard to see and fix.

### Problem 6: `live-signals.ts` — 10Hz deep-compare loop burns CPU

`setInterval(() => this._updateSignals(), 100)` runs 10× per second (`live-signals.ts:204`). Each tick:
1. DOM query for `[data-json-signals]` element
2. `JSON.parse` + `JSON.stringify` roundtrip on the full signal tree
3. `_detectChanges()` — recursive deep object comparison walking every property, allocating `Set`/`Map` per node

For a signal tree with ~50 keys (current app), this is ~5ms per tick = 50ms/sec of pure overhead. This is a dev/debug panel that runs unconditionally in production.

### Problem 7: Timeline rebuilt from scratch after every single op

`_renderTimeline()` (`history-ui.ts:17-124`) is called after every `record()` call (`history-domain.ts:179`). Each rebuild:
1. Allocates 2 Maps + 1 Set
2. For grouped ops: `ops.filter(o => o.groupId === gid)` scans ALL ops per group — O(n²) for n ops with m groups
3. Builds full HTML string with `.map().join()`
4. Sets `innerHTML` (full DOM teardown + rebuild)
5. Re-registers click + dblclick listeners on every chip (O(n) event registrations)

No debouncing. Undo/redo also triggers full rebuild. At 100 ops, this is visible jank.

### Problem 8: Tier manager ticks at 10Hz even when scene is idle

`tier-manager.ts:168`: `setInterval(tick, 100)` calls `window.cadQuery('get_state', {})` every 100ms — a synchronous WASM call — even when no camera movement or scene mutation has occurred. Uses `requestIdleCallback` when available (good), but still ticks unconditionally.

### Problem 9: Sequential boot imports

`boot.ts` lines 32-50: 9 `await import()` calls run sequentially. UI-only modules (`live-signals`, `cf-control-plane`) and custom elements (`cad-outliner`, `cad-gallery`) have no dependency on each other or on WASM, but each waits for the previous to finish loading.

## Decision

### Worker-side

### D1: Codegen Zod schemas and MCP tool list at build time

**Extend the existing `scripts/gen-adapters.ts`** — do NOT create a new script. `gen-adapters.ts` already reads `cad-schema.json` and generates multi-target output (WASM loaders, browser dispatch, Rust metadata). Add a new section that emits `systems/truck/worker/src/cad-schemas.generated.ts`:

```
cad-schema.json (already generated from Rust)
  → scripts/gen-adapters.ts (existing, add new section)
  → cad-schemas.generated.ts (new output)
      exports:
        commandZodSchemas: Record<name, z.ZodObject>
        controlPlaneZodSchemas: Record<name, z.ZodObject>
        mcpToolList: Array<{name, description, inputSchema}>
```

This file is a **committed generated artifact** (like `api-types.ts`). Regenerated by the existing `bun run gen:adapters` command — no new build step needed.

**Deletes at runtime:** `zodFromJsonSchema()` function, `getMcpToolList()` function, all three schema conversion loops.

**Why extend, not create:** `gen-adapters.ts` already has the `cad-schema.json` parsing, the section-based output pattern, and the chain-origin header comment. A new script would duplicate the schema parsing and add another build step to maintain.

### D2: Pre-compute MCP tool definitions at module level

The generated `mcpToolList` from D1 replaces BOTH:
- `registerSchemaTools()`'s per-request Zod construction (currently builds Zod schemas from JSON each time)
- `getMcpToolList()`'s per-request JSON Schema construction (currently rebuilds tool catalog for `/llms-full.txt` and `/server-card.json`)

These two functions currently duplicate the same schema traversal in different output formats. D1's codegen produces both formats once at build time. D2 wires them in:

- `createMcpServer(env)` iterates the pre-built `commandZodSchemas` + `controlPlaneZodSchemas` and calls `server.registerTool()` with pre-built schemas + handler closures that capture `env`
- `/llms-full.txt` and `/server-card.json` use the pre-built `mcpToolList` directly

This reduces per-request MCP cost from "build 29 Zod schemas + register 29 tools" to "register 29 tools with pre-built schemas". Discovery endpoints go from "rebuild JSON Schema catalog" to "return pre-built constant".

### D3: Cache HeadlessController in ModelSession (O(n) → O(1) per command)

**Problem:** `executeServerDirect` replays ALL N ops from scratch on every MCP command. The 10th `add_cube` replays all 10 ops. `replayModel()` can't replace this because it returns `sceneJson` (full scene export), but `executeServerDirect` needs `lastResult` (the individual command output, e.g. `{id, name: "Box 1"}`).

**Fix:** Cache the `HeadlessController` WASM instance in `ModelSession` alongside its op count. This works because `ModelSession` already persists in-memory across requests within the same CF Worker isolate (the `models` Map relies on this).

Add to `ModelSession`:
```ts
interface ModelSession {
  // ... existing fields ...
  cachedCtrl?: HeadlessController;
  cachedCtrlOpCount?: number;
}
```

In `executeServerDirect`, after saving the automerge doc:
```ts
const model = getModel(modelId);
const replayOps = JSON.parse(await syncGetReplayOps(docBytes));

if (model.cachedCtrl && model.cachedCtrlOpCount === replayOps.length - 1) {
  // O(1): execute just the new op on the existing controller
  const lastResult = JSON.parse(model.cachedCtrl.execute(type, JSON.stringify(params)));
  model.cachedCtrlOpCount = replayOps.length;
  return { id: opId, status: 'done', result: lastResult };
} else {
  // Cache miss: full replay, then cache the controller
  const wasm = await initHeadlessWasm();
  const ctrl = new wasm.HeadlessController();
  let lastResult: any = null;
  for (const rop of replayOps) {
    lastResult = JSON.parse(ctrl.execute(rop.type, JSON.stringify(rop.params)));
  }
  model.cachedCtrl = ctrl;
  model.cachedCtrlOpCount = replayOps.length;
  return { id: opId, status: 'done', result: lastResult };
}
```

Additionally, after replay, warm the R2 scene cache so subsequent reads (scene endpoint, `/llms-full.txt`) get a cache hit without replaying:
```ts
// Fire-and-forget: warm scene cache in R2 for reads
replayModel(modelId, env.MODELS, { forceRefresh: true }).catch(() => {});
```

**`replay.ts` must also use the cached controller.** Currently `replayModel()` creates its own ephemeral `HeadlessController` on every call (replay.ts lines 62-66). When a cached controller exists in the session and its op count matches, `replayModel` should use it to export the scene instead of replaying from scratch. Pass the cached controller as an optional parameter:
```ts
export async function replayModel(
  modelId: string, bucket: R2Bucket,
  opts?: { forceRefresh?: boolean; cachedCtrl?: HeadlessController; cachedOpCount?: number }
): Promise<ReplayResult | null>
```

This avoids the same "two places creating ephemeral controllers" duplication that Problem 1 identifies for Zod schemas.

**Performance:** Sequential MCP calls go from O(n) replay to O(1) single-op execution. The cached controller is freed when `gcModels()` evicts the session (5 min idle, already implemented in ADR-0001).

### D4: Throttle `gcModels` to once per 60s

Replace:
```ts
.use('/api/*', async (_c, next) => { gcModels(); return next(); })
```
With:
```ts
let _lastGc = 0;
.use('/api/*', async (_c, next) => {
  const now = Date.now();
  if (now - _lastGc > 60_000) { gcModels(); _lastGc = now; }
  return next();
})
```

### D5: Split index.ts into focused modules

Extract along the existing section boundaries in `index.ts` (marked by `// ====` headers):

| File | Lines | Actual sections being extracted |
|------|-------|-------------------------------|
| `schemas.ts` | 15-101 | `Bindings` type, `ModuleSchema` interface, hand-written Zod schemas (CommandQueued, ModelIdParam, etc.) |
| `session.ts` | 132-235 | "Per-model state & Event Bus" + "SSE Logic" — `ModelSession`, `models` Map, `getModel`, `broadcast`, `gcQueue`, `gcModels`, `enqueueCommand`, `waitForCommand` |
| `server-direct.ts` | 237-291 | "Server-direct execution" — `executeServerDirect` |
| `cad-routes.ts` | 293-428 | "mountModule()" — the dynamic route factory (after D1, no longer needs `zodFromJsonSchema`) |
| `model-routes.ts` | 430-519 | "Headless WASM test" + "Model Persistence REST API" — WASM health check, model CRUD routes |
| `op-log-routes.ts` | 521-693 | "Op Log" + "Scene cache routes" — D1-backed sync, sync-doc, history, scene.json endpoints |
| `mcp-tools.ts` | 741-960 | "MCP" — `registerSchemaTools`, `registerPlatformTools`, `registerModelTools`, `createMcpServer`, `/mcp` mount |
| `discovery.ts` | 963-1127 | llms.txt, llms-full.txt, robots.txt, security.txt, agent.json, server-card.json, docs redirects |

`index.ts` keeps: imports, CORS middleware, health endpoint, sync schema endpoint, route assembly (lines 695-740), SPA fallback (lines 1128-1142), `export default app`.

**Note:** Lines 103-130 (`zodFromJsonSchema`) are deleted by D1 (codegen), not extracted. Existing files (`doc-store.ts`, `model-store.ts`, `replay.ts`, `*-wasm.generated.ts`) are untouched.

**Constraints:**
- **Move-only, no new logic.** Every line in a new file must come from `index.ts` — cut-and-paste, not rewrite. No new abstractions, no new helpers, no "while we're at it" improvements.
- **No duplication.** If code already exists in `doc-store.ts`, `model-store.ts`, `replay.ts`, or `*-wasm.generated.ts`, do not copy it into a new file. Import it.
- **Net line count must decrease.** `index.ts` shrinks by the exact number of lines extracted. Total lines across all files should be equal or fewer (removing the `zodFromJsonSchema` section deleted by D1).
- **Preserve external imports.** `export type AppType = typeof app` and `export default app` must stay in `index.ts` — `scripts/seed-gallery.ts` and `index.test.ts` import them. No other module imports from `index.ts` (all helpers are currently module-private).
- **This is a refactor with no behavior change.** The split makes D1-D4 easier to review and maintain, but the performance wins come from D1-D4, not the split itself.

### D6: Pre-compute static response strings at module level

Move static text (robots.txt, security.txt) to module-level `const` strings instead of rebuilding template literals per request. Minor but free.

### Browser-side

### D7: Gate live-signals polling on visibility (Problem 6)

The `<live-signals>` custom element is a dev/debug inspector. It should not burn CPU in the background.

Replace the unconditional 100ms `setInterval` with:
1. **Only poll when the panel is visible** — check `this.offsetParent !== null` or use an `IntersectionObserver`.
2. **Reduce frequency to 500ms** — signal changes don't need 10Hz resolution for a debug panel.
3. **Skip the deep-compare when `JSON.stringify` matches** — the stringify comparison on `live-signals.ts:227` already gates the expensive `_detectChanges()`, but the JSON roundtrip itself (parse + stringify) still runs 10× per second. Cache the raw `textContent` string and skip entirely if unchanged.

**Net effect:** From ~50ms/sec CPU to near-zero when panel is hidden (common case), and ~10ms/sec when visible.

### D8: Debounce timeline rebuild + fix O(n²) group scan (Problem 7)

Two changes in `history-ui.ts`:

**8a: Debounce `_renderTimeline`** — after `record()` in `history-domain.ts:179`, debounce the timeline rebuild by 100ms. Rapid operations (paste 5 cubes, undo 3 times) coalesce into one rebuild instead of N.

**8b: Pre-index groups** — replace the O(n²) `ops.filter(o => o.groupId === gid)` on line 68 with a single pre-pass:
```ts
const groupMap = new Map<string, typeof ops>();
for (const op of ops) {
  if (op.groupId) {
    let g = groupMap.get(op.groupId);
    if (!g) { g = []; groupMap.set(op.groupId, g); }
    g.push(op);
  }
}
```
Then look up `groupMap.get(gid)` instead of filtering. O(n) total instead of O(n × m).

**8c: Use event delegation** — replace per-chip click/dblclick listeners (lines 106-121) with a single listener on the strip container:
```ts
strip.addEventListener('click', (e) => {
  const btn = (e.target as HTMLElement).closest('[data-chip]');
  if (!btn) return;
  const ci = parseInt((btn as HTMLElement).dataset.chip!);
  // ... same logic
});
```
One listener instead of N. Survives innerHTML rebuilds without re-registration.

### D9: Gate tier-manager ticks on scene mutation (Problem 8)

`tier-manager.ts` calls `cadQuery('get_state')` every 100ms unconditionally. Gate it:

```ts
let _sceneDirty = true;
export function markSceneDirty() { _sceneDirty = true; }

async function _tickInner() {
  if (!_sceneDirty) return;
  _sceneDirty = false;
  // ... existing tick logic
}
```

Call `markSceneDirty()` from:
- `cadCommand()` after any mutation
- Camera change events (orbit, zoom, pan)
- Window resize

When the scene is idle (no user interaction), tick becomes a no-op. Saves ~10 sync WASM calls/sec.

### D10: Parallelize boot imports (Problem 9)

Group independent imports in `boot.ts` lines 32-50:

```ts
// Phase 1: UI + WASM in parallel (no interdependency)
const [, , wasmModule] = await Promise.all([
  import('./live-signals'),
  import('./cf-control-plane'),
  import('./pkg-browser-renderer/truck_webgpu_gui.js'),
]);
window.__wasmInit = wasmModule.default;
window.__SceneController = wasmModule.SceneController;

// Phase 2: Custom elements (need WASM for cad-viewport)
await import('./cad-viewport');
await Promise.all([import('./cad-outliner'), import('./cad-gallery')]);

// Phase 3: Core modules (depend on custom elements being registered)
await Promise.all([
  import('./state'),
  import('./history-ui'),
  import('./ui'),
  import('./keyboard'),
  import('./sketch'),
]);
```

**Constraint:** `cad-viewport` must await WASM. `cad-outliner` and `cad-gallery` can parallelize. State/history/ui/keyboard/sketch have no sequential dependency on each other — they wire globals and event listeners.

## Implementation Order

### Quick wins (1-line to small changes, land independently)
1. **D4** — gcModels throttle (1 line)
2. **D6** — static response strings (move literals to module-level consts)
3. **D7** — gate live-signals on visibility (biggest browser CPU win)

### Worker perf (land together after quick wins)
4. **D1** — codegen in gen-adapters.ts + generated file
5. **D2** — pre-compute MCP tool defs (depends on D1)
6. **D3** — cache HeadlessController in session

### Browser perf (independent of each other)
7. **D8** — debounce timeline + fix O(n²) + event delegation
8. **D9** — gate tier-manager on scene mutation

### Refactor (last, no behavior change)
10. **D5** — file split (once everything else is stable)

## Validation

**Correctness:** Existing tests (`index.test.ts`, 30 tests) cover behavior — if they pass, nothing broke.

### Worker benchmarks: workerd-native vitest (no mocks)

**Prerequisite:** Tests are being migrated from mock R2 to `@cloudflare/vitest-pool-workers` (separate effort in progress). This runs vitest inside the real workerd runtime with real R2 bindings, WASM, and Cloudflare APIs — no mocks needed.

Once that lands, benchmarks run in the same environment as production. This means:
- **Real R2 latency** — D3's cached controller saves actual R2 reads, not instant mock reads
- **Real WASM init** — cold start timing is genuine
- **Real isolate behavior** — module-level state persistence (used by D3, D4) works identically to production
- **One layer, not two** — no need for a separate "live system" benchmark script

Add `src/index.bench.ts` (vitest bench file, runs via `vitest bench` in the workerd pool):

```ts
import { bench, describe } from 'vitest';
import { env } from 'cloudflare:test';  // real R2, real bindings

const mcpBody = (i: number, modelId: string) => JSON.stringify({
  jsonrpc: '2.0', id: i, method: 'tools/call',
  params: { name: 'cad_add_cube', arguments: { size: 1, modelId } },
});
const mcpHeaders = { 'content-type': 'application/json', accept: 'application/json' };

describe('MCP perf', () => {
  bench('single cad_add_cube (warm)', async () => {
    const worker = await import('./index');

    }, env);

    const mid = `bench-seq-${Date.now()}`;

```

## Consequences

### Positive
- **Faster cold start:** No runtime schema conversion (~42 Zod objects eliminated from module init)
- **Faster MCP:** Pre-built schemas, no per-request Zod construction
- **Faster sequential MCP commands:** Cached HeadlessController gives O(1) per command instead of O(n) full replay
- **DRY:** One codegen script replaces three runtime conversion paths
- **Maintainable:** 7 focused files instead of 1,146-line monolith
- **Browser idle CPU near zero:** Live-signals gated on visibility, tier-manager gated on mutation — no background polling when scene is idle
- **Smoother editing at scale:** Timeline rebuild debounced + O(n) group indexing — no jank at 100+ ops
- **Faster boot:** Parallel imports reduce sequential WASM wait

### Negative
- **One more output from `gen-adapters.ts`** — but no new build step; the existing `bun run gen:adapters` command picks it up
- **Generated file must be kept in sync** (same as `api-types.ts` — already solved by `bun run build:truck`)

### Risks
- **MCP SDK may not support pre-built tool registration well** — if `McpServer` requires tools registered during construction, D2 may need to keep per-request registration but with pre-built schemas (still a win)
- **Cached HeadlessController holds WASM memory** — one controller per active model session, freed by `gcModels()` on 5-min idle. If many models are active simultaneously, memory pressure increases. Mitigated: CF Workers have 128MB limit per isolate, and each HeadlessController is small (scene state only, no mesh data)
- **Cache invalidation on external doc changes** — if another actor (browser, different isolate) modifies the automerge doc, the cached controller's op count won't match and falls back to full replay. This is correct behavior (safe fallback), not a bug.
