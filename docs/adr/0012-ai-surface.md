# [ADR-012] AI Surface — Single Source of Truth for AI Discovery

## Intent

The project needs a coherent strategy for how AI assistants discover, understand, and interact with the system. Today we have multiple overlapping files (AGENT.md, CLAUDE.md, GEMINI.md, skills, llms.txt, MCP, schema) with no clear contract for what goes where. This ADR defines the single-source architecture so nothing drifts and nothing duplicates.

## Status

**In Progress** — AGENT.md, CLAUDE.md, GEMINI.md, MCP, and schema chain are implemented. `/llms.txt` route added. Skills and llms-full.txt for upstream deps exist.

## Context

AI assistants interact with this project at multiple levels:

1. **Coding on the repo** — Claude Code, Gemini CLI, Cursor, etc. reading source files
2. **Driving the CAD via MCP** — AI agents calling tools like `cad_add_cube`
3. **Discovering the project** — Any AI fetching `cad.ubuntusoftware.net/llms.txt`
4. **Learning upstream deps** — AI needing Automerge or kkrpc API knowledge

Each level needs different information, but it must all derive from the same sources. Hand-written copies drift. Generated artifacts stay in sync.

## Decision: Two Sources, Everything Derived

### Source 1: Rust Structs (machine contract)

```
Rust param structs (#[derive(Deserialize, JsonSchema)])
  → cargo run --bin generate-schema
  → web/cad-schema.json (generated, checked into git)
    → Worker Zod validation (generated at import time)
    → MCP tool registration (generated at import time)
    → OpenAPI spec (generated at import time)
    → /api/cad/schema endpoint (serves the JSON)
    → Per-command HTTP routes (generated by mountModule())
```

This chain is fully automated. Add a command in Rust → `task truck:gui:build` → everything updates. No human touches the downstream artifacts.

### Source 2: AGENT.md (human/AI contract)

```
AGENT.md (hand-maintained, the WHY + HOW)
  → CLAUDE.md    (reads AGENT.md)
  → GEMINI.md    (reads AGENT.md)

web/llms.txt (hand-maintained, external-facing summary)
  → /llms.txt    (served at the web root for external AI discovery)
```

AGENT.md contains what the schema cannot: architecture decisions, workflow conventions, file locations, AI agent rules, the project's purpose. It's the internal developer context for AI coding agents.

`web/llms.txt` is a concise, external-facing summary for AI discovering the project via its URL — MCP connection info, API endpoints, deployed URLs. It changes rarely.

## Rules

1. **AGENT.md is the single human-readable source.** CLAUDE.md and GEMINI.md must NOT duplicate content — they say "Read AGENT.md first" and add only tool-specific config.

2. **cad-schema.json is the single machine-readable source.** Worker Zod, MCP tools, OpenAPI, and per-command routes are ALL generated from it. No hand-written tool registrations.

3. **Never duplicate between the two sources.** AGENT.md describes architecture and conventions. cad-schema.json describes commands and parameters. They complement, not overlap.

4. **Skills are curated lenses, not copies.** `.claude/skills/automerge/SKILL.md` points into `docs/llms/automerge-llms-full.txt` with project-specific guidance. It does not copy the upstream docs.

5. **`/llms.txt` serves `web/llms.txt`, a concise external-facing summary.** AGENT.md is internal developer context; llms.txt is for external AI discovery (MCP connection, API endpoints, URLs).

6. **Upstream docs go in `docs/llms/`.** When a dependency publishes an `llms-full.txt`, fetch it there. Both Claude and Gemini can reference it from AGENT.md.

## What Each AI Gets

### Claude Code (coding in the repo)
- Reads: `CLAUDE.md` → `AGENT.md` → source files
- Skills: `/automerge`, `/kkrpc`, `/interop` (slash commands)
- MCP: `truck-cad` via bridge in `.mcp.json` (stdio → Worker `/mcp`)
- Deep docs: `docs/llms/*.txt` when needed

### Gemini CLI (coding in the repo)
- Reads: `GEMINI.md` → `AGENT.md` → source files
- MCP: `truck-cad` via bridge (`scripts/mcp-bridge.ts` → Worker `/mcp`)
- MCP: `playwright` with WebGPU launch args (`scripts/playwright-mcp.config.json`)
- Both configured by `task truck:mcp:setup` → `.gemini/settings.json`
- Deep docs: `docs/llms/*.txt` when needed
- No skills system (reads the same files manually when needed)

### External AI (hitting the deployed URL)
- Fetches: `cad.ubuntusoftware.net/llms.txt` → concise project summary + MCP connection info
- MCP: connects to `/mcp` directly (stateless JSON-RPC) or via bridge with `CAD_URL=https://cad.ubuntusoftware.net`
- API: `/api/openapi.json` → full HTTP API reference
- Schema: `/api/cad/schema` → raw command catalog

## MCP Server Configuration

### Architecture: Single implementation, unified proxy

**Worker `/mcp`** is the single MCP implementation — stateless JSON-RPC handling `initialize`, `tools/list`, and `tools/call`. It dispatches to the same `waitForCommand()` pipeline as REST. 29 tools total (27 CAD commands + `cad_health` + `cad_schema` meta-tools). No SDK at runtime — just JSON-RPC over HTTP POST.

**Bridge** (`scripts/mcp-bridge.ts`) is a pure stdio ↔ HTTP proxy (~65 lines). It adds:
- **Retry** with exponential backoff (6 attempts, 1s → 32s) — survives dev server restarts
- **Schema version polling** (every 30s) → sends `tools/list_changed` notification — hot-reload without client restart

The bridge works identically for dev and production — just change `CAD_URL`:

```
AI tool ←→ stdio ←→ mcp-bridge.ts (never restarts)
                         ↕ HTTP POST /mcp with retry
                    Worker /mcp endpoint
                    (may restart during dev — bridge retries)
```

### Solved problems

**Problem 1 — Startup**: Bridge starts instantly (no server connection needed). First tool call triggers retry if server isn't ready yet.

**Problem 2 — Dev-loop restarts**: Bridge retries transparently. Server can restart 100 times without AI losing tools.

**Problem 3 — Production hot-reload**: Bridge polls schema version every 30s. Deploy new code → bridge detects version change → sends `tools/list_changed` → client re-fetches tools. No restart.

**Problem 4 — Dual implementations**: Previously the bridge built its own tool list from the schema file and proxied to REST sync routes. Now it's a pure proxy to Worker `/mcp` — ONE tool list, ONE dispatch path.

### Per-tool configuration

| Tool | Config file | Transport | Hot-reload |
|------|-----------|-----------|------------|
| Claude Code | `.mcp.json` | stdio → bridge → Worker `/mcp` | Version polling (30s) |
| Gemini CLI | `.gemini/settings.json` | stdio → bridge → Worker `/mcp` | Version polling (30s) |
| Cursor | `.cursor/mcp.json` | stdio → bridge → Worker `/mcp` | Version polling (30s) |
| Direct HTTP | Any MCP client | `"type": "http"` → Worker `/mcp` | Manual restart only |
| Playwright MCP | `.gemini/settings.json` | stdio → `@playwright/mcp` | Independent |

All AI coding tools use the bridge for retry + hot-reload. Direct HTTP is available for simpler integrations (no bridge install needed).

### Files

```
scripts/mcp-bridge.ts              — Pure stdio ↔ HTTP proxy (~65 lines)
scripts/mcp-setup.sh               — Writes .gemini/settings.json, .cursor/mcp.json
scripts/mcp-teardown.sh            — Clears MCP configs
scripts/playwright-mcp.config.json — WebGPU-enabled Playwright browser launch args
```

### Summary

| Concern | Solution |
|---------|----------|
| Single MCP implementation | Worker `/mcp` (stateless JSON-RPC, 29 tools) |
| Schema contract | `cad-schema.json` (Rust-generated, cleaned at compile time) |
| All AI tools MCP | Stdio bridge → Worker `/mcp` (retry + hot-reload) |
| Production users | Direct HTTP to `/mcp` or bridge with `CAD_URL=https://...` |
| Playwright MCP | Global config with WebGPU launch args |
| Config lifecycle | `task truck:mcp:setup` / `mcp:teardown` |
| Server restarts | Bridge retries transparently (6 attempts, exponential backoff) |
| Hot-reload on deploy | Bridge polls schema version → `tools/list_changed` notification |
