# [ADR-012] AI Surface — Single Source of Truth for AI Discovery

## Intent

The project needs a coherent strategy for how AI assistants discover, understand, and interact with the system. Today we have multiple overlapping files (CONTEXT.md, CLAUDE.md, GEMINI.md, skills, llms.txt, MCP, schema) with no clear contract for what goes where. This ADR defines the single-source architecture so nothing drifts and nothing duplicates.

## Status

**In Progress** — CONTEXT.md, CLAUDE.md, GEMINI.md, MCP, and schema chain are implemented. `/llms.txt` route added. Skills and llms-full.txt for upstream deps exist.

## Context

AI assistants interact with this project at multiple levels:

1. **Coding on the repo** — Claude Code, Gemini CLI, Cursor, etc. reading source files
2. **Driving the CAD via MCP** — AI agents calling tools like `cad_add_cube`
3. **Discovering the project** — Any AI fetching `cad.ubuntusoftware.net/llms.txt`
4. **Learning upstream deps** — AI needing Automerge or kkrpc API knowledge

Each level needs different information, but it must all derive from the same sources. Hand-written copies drift. Generated artifacts stay in sync.

## Decision: Two Sources, Everything Derived

### Source 1: Rust Structs (machine contract)

```
Rust param structs (#[derive(Deserialize, JsonSchema)])
  → cargo run --bin generate-schema
  → web/cad-schema.json (generated, checked into git)
    → Worker Zod validation (generated at import time)
    → MCP tool registration (generated at import time)
    → OpenAPI spec (generated at import time)
    → /api/cad/schema endpoint (serves the JSON)
    → Per-command HTTP routes (generated by mountModule())
```

This chain is fully automated. Add a command in Rust → `task truck:gui:build` → everything updates. No human touches the downstream artifacts.

### Source 2: CONTEXT.md (human/AI contract)

```
CONTEXT.md (hand-maintained, the WHY + HOW)
  → CLAUDE.md    (reads CONTEXT.md + Claude-specific config)
  → GEMINI.md    (reads CONTEXT.md + Gemini-specific config)
  → /llms.txt    (serves CONTEXT.md at the web root)
```

CONTEXT.md contains what the schema cannot: architecture decisions, workflow conventions, file locations, AI agent rules, the project's purpose. It's the single place a human or AI goes to understand the project.

### The Full Picture

```
                    Rust structs
                        │
```

## File Roles

| File | Maintained by | Read by | Purpose |
|------|--------------|---------|---------|
| `CONTEXT.md` | Human + AI | All AI assistants in the repo | Project understanding (the WHY) |
| `CLAUDE.md` | Human | Claude Code | "Read CONTEXT.md" + Claude-specific settings |
| `GEMINI.md` | Human | Gemini CLI | "Read CONTEXT.md" + Gemini-specific settings |
| `cad-schema.json` | Generated from Rust | Worker, tests | Machine-readable command contract |
| `/llms.txt` | Served from CONTEXT.md | Any AI on the web | External discovery |
| `/api/cad/schema` | Served from cad-schema.json | MCP clients, API consumers | Runtime tool discovery |
| `/mcp` | Generated from schema | AI agents (Claude, Cursor, etc.) | Runtime tool execution |
| `/api/openapi.json` | Generated from schema | API docs (Scalar UI) | HTTP API reference |
| `docs/llms/*.txt` | Fetched from upstream | AI needing dep knowledge | Automerge, kkrpc full docs |
| `.claude/skills/` | Human (curated) | Claude Code slash commands | Focused patterns per library |
| `.claude/settings.json` | Human | Claude Code | MCP server config (truck-cad) |
| `.gemini/settings.json` | Human | Gemini CLI | MCP server config (truck-cad via mcp-remote) |

## Rules

1. **CONTEXT.md is the single human-readable source.** CLAUDE.md and GEMINI.md must NOT duplicate content — they say "Read CONTEXT.md first" and add only tool-specific config.

2. **cad-schema.json is the single machine-readable source.** Worker Zod, MCP tools, OpenAPI, and per-command routes are ALL generated from it. No hand-written tool registrations.

3. **Never duplicate between the two sources.** CONTEXT.md describes architecture and conventions. cad-schema.json describes commands and parameters. They complement, not overlap.

4. **Skills are curated lenses, not copies.** `.claude/skills/automerge/SKILL.md` points into `docs/llms/automerge-llms-full.txt` with project-specific guidance. It does not copy the upstream docs.

5. **`/llms.txt` serves CONTEXT.md, not a separate file.** One file, one URL, zero drift.

6. **Upstream docs go in `docs/llms/`.** When a dependency publishes an `llms-full.txt`, fetch it there. Both Claude and Gemini can reference it from CONTEXT.md.

## What Each AI Gets

### Claude Code (coding in the repo)
- Reads: `CLAUDE.md` → `CONTEXT.md` → source files
- Skills: `/automerge`, `/kkrpc`, `/interop` (slash commands)
- MCP: `truck-cad` via `.claude/settings.json` (native URL type)
- Deep docs: `docs/llms/*.txt` when needed

### Gemini CLI (coding in the repo)
- Reads: `GEMINI.md` → `CONTEXT.md` → source files
- MCP: `truck-cad` via `.gemini/settings.json` (mcp-remote bridge)
- Deep docs: `docs/llms/*.txt` when needed
- No skills system (reads the same files manually when needed)

### External AI (hitting the deployed URL)
- Fetches: `cad.ubuntusoftware.net/llms.txt` → CONTEXT.md content
- MCP: connects to `/mcp` → gets tool descriptions + schemas
- API: `/api/openapi.json` → full HTTP API reference
- Schema: `/api/cad/schema` → raw command catalog

## MCP Server Configuration

### The chicken-and-egg problem

The CAD MCP server (`truck-cad`) runs on `localhost:8787` — the same dev server we're building. If an AI tool config tries to connect on startup, it fails because the server isn't running yet.

**Claude Code** handles this gracefully: `"type": "url"` is lazy — it only connects when you actually call a tool. So the config lives in `.claude/settings.json` permanently and just works.

**Gemini CLI** does NOT handle this: `mcp-remote` starts a subprocess immediately on startup. If the server isn't running, Gemini fails to start. So `.gemini/settings.json` must NOT include truck-cad by default.

| Tool | Config file | Transport | Startup behavior |
|------|-----------|-----------|-----------------|
| Claude Code | `.claude/settings.json` | `"type": "url"` (lazy) | Connects on first tool call — safe to always configure |
| Gemini CLI | `.gemini/settings.json` | `bunx mcp-remote` (eager) | Connects immediately — fails if server is down |

### Solution: Taskfile manages MCP configs

The Taskfile already manages the server lifecycle (`gui:serve`, `up`, `down`). It should also manage the MCP configs that depend on that server. This is the control plane pattern (ADR-011): the system manages its own state transitions.

**`task truck:mcp:setup`** — writes MCP configs for all AI tools:
```yaml
truck:mcp:setup:
  desc: Configure MCP settings for all AI tools
  cmds:
    - scripts/mcp-setup.sh
```

**`scripts/mcp-setup.sh`** — generates `.gemini/settings.json`, `.cursor/mcp.json`, etc. from a template, parameterized by the server URL. Idempotent — safe to run multiple times.

**`task truck:mcp:teardown`** — removes MCP configs (restores empty settings):
```yaml
truck:mcp:teardown:
  desc: Remove MCP settings (server not running)
  cmds:
    - scripts/mcp-teardown.sh
```

**Integration with server lifecycle**:
```yaml
truck:gui:serve:
  deps: [truck:mcp:setup]       # configure MCP before serving
  cmds:
    - wrangler dev ...

# process-compose can call mcp:teardown on exit
```

**Health-check wrapper** — for tools where the config must exist permanently but the server may not be running:

`scripts/mcp-wait.sh`:
```bash
#!/bin/bash
# Wait for dev server health, then bridge MCP
until curl -sf http://localhost:8787/health >/dev/null 2>&1; do sleep 2; done
exec bunx -y mcp-remote "$1"
```

`.gemini/settings.json` (when using wrapper approach):
```json
{
  "mcpServers": {
    "truck-cad": {
      "command": "./scripts/mcp-wait.sh",
      "args": ["http://localhost:8787/mcp"]
    }
  }
}
```

This gives two options per tool:
1. **Taskfile-managed**: `mcp:setup` writes config → `gui:serve` starts server → MCP works. `mcp:teardown` on stop.
2. **Wrapper-managed**: Config is permanent, script waits for server. No Taskfile coupling.

Claude Code needs neither — its lazy `"type": "url"` just works.

### Summary

| Tool | Strategy | Config lifecycle |
|------|----------|-----------------|
| Claude Code | Lazy URL (built-in) | Permanent in `.claude/settings.json` |
| Gemini CLI | Taskfile-managed OR health-check wrapper | Written by `task truck:mcp:setup` OR permanent with `mcp-wait.sh` |
| Cursor / other | Taskfile-managed | Written by `task truck:mcp:setup` |

Global AI tool configs (Playwright, fetch) go in `~/.claude/` or `~/.gemini/`. Project-specific MCP configs are managed by the Taskfile as part of the server lifecycle.

## Open Questions

- Should `/llms.txt` also append the schema JSON for a complete picture? (CONTEXT.md = WHY, schema = WHAT, combined = everything)
- Should `CONTEXT.md` be auto-generated from ADRs + schema metadata? Or is hand-curation the right trade-off?
- How do we handle llms.txt for future modules? One per module (`/mesh/llms.txt`) or merged?
- Should skills be promoted to a shared format (not Claude-specific) so Gemini can invoke them too?
