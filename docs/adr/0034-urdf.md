# [ADR-0034] URDF Robot Integration

## Status

**Proposed**. Initial research phase (Phase 0).

## Context

To enable robotic simulation and reachability analysis within the CAD system, we need to support **URDF (Unified Robot Description Format)**. URDF is the industry standard for describing robot kinematics (links and joints) and is used by most robot manufacturers (including those in China and elsewhere).

Integrating URDF allows users to:
- Import robot models directly into the CAD workspace.
- Validate if a designed product can be handled by a specific robot (clash detection, workspace reach).
- Simulate kinematic movements (joint rotation/translation) within the CAD kernel.

URDF is an XML-based format that differs significantly from our existing B-Rep (STEP) and Semantic BIM (IFC) formats, as it defines a **kinematic tree** rather than a flat collection of parts.

## Decision

Leverage the existing `truck-assembly` crate to manage robot kinematics, mapping URDF links to `Node`s and URDF joints to `Edge`s in a Directed Acyclic Graph (DAG).

### 1. Data Model: Kinematic DAG (`truck-assembly`)

We will utilize `truck_assembly::dag::Dag<LinkEntity, JointEntity>` to represent the robot structure:
- **`LinkEntity` (Node)**: Stores the visual/collision `PolygonMesh` and metadata (inertial properties, mass).
- **`JointEntity` (Edge)**: Stores the joint type (fixed, revolute, prismatic, continuous), axis of movement, and current **joint value** (angle or displacement).

By using the `Dag` structure from `truck-assembly`, we can use its built-in `maximal_paths_iter` and `matrix()` methods to recursively calculate the world-space transform for any link relative to the base frame.

### 2. Efficient Kinematic Updates

Instead of rebuilding the underlying B-Rep geometry for every joint movement (which is computationally expensive), we will:
1. Store the local transform (origin + current joint value) in each `JointEntity` (Edge).
2. Perform a lazy tree traversal starting from the `base_link` whenever a joint value changes.
3. Compute the accumulated `Matrix4` for each link.
4. Update the `instance_state.matrix` of the corresponding `PolygonInstance` on the GPU directly.

This approach ensures 60fps interactive "posing" of the robot even with complex multi-link chains.

### 3. Proposed Commands (Schema)

To support URDF, we will add the following commands to `cad-schema.json`:

| Command | Domain | Purpose |
|---------|--------|---------|
| `import_urdf` | `scene` | Parse URDF XML and load all link geometries into a `truck-assembly` DAG. |
| `set_joint_value` | `geometry` | Update a specific joint's state (revolute/prismatic) and trigger matrix refresh. |
| `get_kinematic_tree` | `style` | Return the robot hierarchy and current joint limits/values from the DAG. |

### 4. Implementation Strategy

#### Phase 1: URDF Ingestion
- Use a lightweight XML parser (e.g., `roxmltree`) to parse the URDF file.
- Support visual elements in `.stl` (via `truck-polymesh`) and basic primitives (box, cylinder, sphere).
- Build the initial `Dag` structure in `SharedState`.

#### Phase 2: Kinematic Propagation
- Implement a `refresh_robot_transforms()` method that traverses the `Dag` and updates world-space positions.
- Connect this to the existing `SceneController` rendering loop.

#### Phase 3: Collision-Aware Reachability
- Use `truck-shapeops` (via the existing `clash_detect` command) to check for self-collisions and collisions between the robot's end-effector and the product being designed.

### 5. Hybrid Geometry & Asset Loading

URDF files typically reference external 3D assets for visual and collision representation. We will support a hybrid approach:
- **Primitives**: If the URDF defines `<box>`, `<cylinder>`, or `<sphere>`, we will generate native **B-Rep Solids** using the `truck-modeling` primitives (`make_cube`, etc.). This allows for high-precision clash detection against the product.
- **Meshes**: If the URDF references external `.stl` or `.obj` files via the `<mesh>` tag, we will use **`truck-polymesh`** to ingest them. These will be treated as **Reference Meshes**—perfect for visual fidelity and fast GPU rendering via `PolygonInstance`.
- **Resource Resolution**: Since URDF often uses `package://` URLs, the JS layer will handle resolving these paths to either local Blobs (from a user-uploaded ZIP) or remote URLs before passing the data to the WASM kernel.

### 6. Kinematic Solver Architecture

To support both manual posing (FK) and automated target-reaching (IK), the kernel will implement two distinct solver layers:

- **Forward Kinematics (FK) - Tree Traversal**:
  This is the default mode. When a user adjusts a joint value (e.g., via a slider), the kernel performs a single pass through the `truck-assembly` DAG. It calculates the global `Matrix4` for each child link by multiplying the parent's global transform with the joint's local transform ($T_{global} = T_{parent} \times T_{joint}$). This is a $O(N)$ operation where $N$ is the number of links.

- **Inverse Kinematics (IK) - Iterative Solver**:
  To support "drag-to-position" interactions, we will implement an iterative solver (such as **Cyclic Coordinate Descent (CCD)** or a **Jacobian-based** method). 
  - **Input**: A target world-space coordinate $(x, y, z)$ for the "End-Effector" link.
  - **Process**: The solver will iteratively adjust the `joint_value` in each `JointEntity` (Edge) to minimize the distance between the End-Effector's current position and the target.
  - **Constraints**: The solver will respect the `<limit>` tags defined in the URDF (lower/upper bounds for angles or displacement).

- **Interaction Loop**:
  The solver updates the `joint_value` in the `SharedState` -> The DAG computes new matrices -> The GPU instances are updated. This decoupling ensures that even complex IK calculations do not stall the rendering pipeline.

### 7. Test Datasets & Reference Models

To validate the implementation, we will use the following URDF models as test cases:

- **Universal Robots (UR-ROS-Driver)**: [UR5/UR10 URDFs](https://github.com/UniversalRobots/Universal_Robots_ROS_Driver/tree/master/ur_description). Essential for validating revolute joints and standard 6-DOF kinematics.
- **Unitree Robotics**: [Unitree ROS Models](https://github.com/unitreerobotics/unitree_ros/tree/master/robots). Complex trees for legged robots (Go1, AlienGo).
- **Aubo Robotics**: [Aubo Description](https://github.com/AuboRobot/aubo_robot/tree/master/aubo_description). Representative of the Chinese collaborative robot market.
- **KUKA LBR iiwa**: [KUKA Description](https://github.com/rtkguest/iiwa_stack/tree/master/iiwa_description). Testing 7-DOF redundant kinematics.
- **NASA Robonaut 2**: [R2 Description](https://github.com/nasa/Robonaut2/tree/master/r2_description). High-complexity model for stress-testing the XML parser and DAG depth.

### 8. Unified Kinematic & Animation Architecture

The URDF integration is not a standalone "import filter" but the primary driver for a **Unified Kinematic Scene Graph**. This architecture explicitly exploits the overlap between imported robot models and user-defined mechanical assemblies:

- **B-Rep as Kinematic Links**: Users building models with `truck-modeling` primitives (B-Reps) can promote any `SceneObject` to a "Link" in the kinematic DAG.
- **Native Joint Creation**: New CAD commands will allow users to define joints *between* their B-Rep parts (e.g., `add_revolute_joint(base_id, arm_id, axis, origin)`). This allows the creation of custom machines directly in the kernel.
- **Shared IK Solver**: Because the solver operates on the `truck-assembly` DAG rather than the geometry itself, the same IK logic handles both complex supplier robots (URDF) and custom user-built mechanisms.
- **Animation Foundation**: By exposing the `joint_value` in the DAG to a temporal controller, we gain a full **Animation System**. A "Keyframe" is simply a recorded state of all `joint_values` in the DAG at a specific time.

### 9. Proposed Integrated Commands (Extended Schema)

| Command | Domain | Purpose |
|---------|--------|---------|
| `create_joint` | `geometry` | Define a kinematic relationship (Revolute/Prismatic) between any two B-Rep solids. |
| `remove_joint` | `geometry` | Break a kinematic link and return parts to the flat scene list. |
| `animate_joint` | `scene` | Interpolate a `joint_value` over time (basis for future timeline). |

### 10. Serialization & Persistence (Vendor Patching)

The `truck-assembly` crate provides a robust DAG structure but currently lacks built-in serialization. To exploit this "missing trick" and ensure long-term architectural integrity, we will:

- **Patch `truck-assembly`**: Add `serde` support (Serialize/Deserialize) directly to the `Dag`, `Node`, and `Edge` types in the vendor source (`.src/truck/truck-assembly`). This ensures the "Kinematic Map" can be saved and reloaded with zero overhead or custom mapping code.
- **Scene Graph Unification**: Update the top-level `SceneExport` to include this serialized `Dag`. When the scene is reloaded, the assembly structure is restored identically to its saved state, including all joint angles and kinematic relationships.
- **Automerge Compatibility**: By making the `Dag` natively serializable, it becomes a first-class citizen in our **Automerge** CRDT layer. Collaborative users will see robot movements and joint changes synchronized with the same performance as standard geometry edits.

## Consequences

- **Performance**: High efficiency for kinematic updates by decoupling topological B-Rep reconstruction from visual instance transforms.
- **Architectural Alignment**: Strong alignment with the `truck` ecosystem by adopting `truck-assembly`.
- **Dependency**: Adding an XML parser is a minimal addition to the WASM bundle.

## Future

- **Inverse Kinematics (IK)**: Integrate a solver to allow "drag-to-position" for the robot end-effector.
- **Dynamic Simulation**: Use the inertial properties in `LinkEntity` to support basic physics-based simulation.
