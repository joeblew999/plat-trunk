# ADR 0035 — Vite + TypeScript for Browser Code

**Status:** Implemented
**Date:** 2026-03-02

## Problem

The browser-side code (`systems/truck/web/`, 18 JS files, ~3,900 lines) had:

1. **No type checking** — bugs only show up at runtime in the browser
2. **Manual vendoring** — 4.8 MB of bundled JS checked into git, rebuilt via custom `update.mjs` with obscure esbuild flags
3. **No hot reload** — manual F5 after every JS change
4. **Separate build step** for API client — `api-client.ts` compiled by esbuild in isolation
5. **Broken Hono RPC types** — `hc<AppType>` doesn't propagate types through `OpenAPIHono + createRoute() + .route()` chains; runtime errors only

## Decision

Migrate `systems/truck/web/` to Vite + TypeScript with proper typed API clients.

Replace broken `hc<AppType>` with `openapi-fetch` + `openapi-typescript`, driven by the same schema-first chain used everywhere else in the system.

## What Does NOT Change

- All workers (Hono server, wrangler configs, service bindings, ports)
- Multi-worker topology (run.mjs, workers.mjs, router, test-worker)
- Rust/WASM build (cargo, wasm-pack, pkg-browser-renderer output)
- Deploy pipeline (cf-deploy.ts)
- Playwright tests (same URLs, same API, same assertions)

## Full API Type Generation Chain

```
Rust (#[derive(Deserialize, JsonSchema)])
  → bun run build:truck          wasm-pack --release + cargo run --bin generate-schema
  → systems/truck/cad-schema.json                     [COMMITTED generated artifact]
  → bun run gen:openapi          scripts/gen-openapi.ts reads cad-schema.json
  → systems/truck/web/openapi.json                    [gitignored intermediate]
  → bun run gen:api-types        openapi-typescript + chain-origin header
  → systems/truck/web/api-types.ts                    [COMMITTED generated artifact]
  → bun run build:truck-web      Vite build (uses api-types.ts via openapi-fetch)
  → systems/truck/web/dist/                           [gitignored, served by wrangler]
```

`bun run build:truck-web` runs the full gen chain automatically — no server needed.

`api-types.ts` is a committed generated artifact, exactly like `cad-schema.json`. Regenerate when API routes change: `bun run gen:api-types`.

## Why openapi-fetch + openapi-typescript (not hc\<AppType\>)

`hc<AppType>` fails silently when:
- Routes are registered via `OpenAPIHono.openapi()` + `createRoute()` + `.route()` chains
- The app uses middleware (`.use()` changes the return type from `OpenAPIHono` to `Hono`)

`openapi-fetch` reads the OpenAPI spec (which IS generated correctly by `@hono/zod-openapi`), producing typed `client.GET(path, opts)` / `client.POST(path, opts)` calls that match the actual runtime API surface.

The OpenAPI spec is the source of truth — it's generated from Rust schema (dynamic routes) and hand-defined Zod routes (stable routes), and served live at `/api/openapi.json`.

```ts
// api-client.ts — typed with zero server coupling
import createClient from 'openapi-fetch';
import type { paths } from './api-types';
export const client = createClient<paths>({ baseUrl: '/' });

// callers get full inference:
const { data } = await client.GET('/api/models', {});            // data: ModelManifest[]
const { data } = await client.PUT('/api/models/{id}', {...});    // body/params typed
```

## Key Design Decisions

### Why Vite (not raw esbuild or webpack)
- Native WASM support via `vite-plugin-wasm` (same approach as ifc-lite viewer in this repo)
- `@tailwindcss/vite` plugin for Tailwind v4 — no PostCSS config needed
- Built-in dev server with HMR and API proxy to wrangler
- `bun run build` produces identical output to dev (`dist/` served by wrangler ASSETS)

### Why NOT `@cloudflare/vite-plugin`
- Would require restructuring multi-worker topology
- Our workers run as separate `wrangler dev` processes — established pattern
- Vite for frontend, wrangler for workers — clean separation

### Why Datastar stays self-hosted
- Not published to npm (CDN/self-hosted distribution model)
- Hypermedia framework that scans `data-*` attributes — doesn't benefit from bundling

### Why openapi-fetch over hc\<AppType\>
- `hc<AppType>` type inference breaks with `OpenAPIHono + .route()` chains
- `openapi-fetch` reads the generated spec — same source of truth as MCP tools
- Client types flow from the OpenAPI spec, not from TypeScript across package boundaries

## Infrastructure Changes

| What | Before | After |
|------|--------|-------|
| `wrangler.toml` assets | `directory = "../web"` | `directory = "../web/dist"` |
| API client | `hc<AppType>` from hono/client | `createClient<paths>` from openapi-fetch |
| API types | manual hand-written types | generated by `bun run gen:api-types` |
| Dev server | no dedicated server (F5 to reload) | Vite at :5173 with HMR |
| Build | esbuild one-off + watcher | `vite build` → `dist/` |
| Vendor libs | 4.8 MB committed JS bundles | npm deps, bundled by Vite |
| TypeScript coverage | `api-client.ts` only | all 19 `.ts` files |
| Root `typecheck` | worker only | worker + web |

## Deleted

- `vendor/` directory (~4.8 MB of bundled JS removed from git)
- `vendor/update.mjs` (no longer needed)
- `src/` directory (files moved to root)
- CDN dependency on jsdelivr.net for Tailwind + DaisyUI
- `build:api-client` build step
- `watch-api-client` dev server

## Verification

- `bun run build:truck-web` → Vite build succeeds, outputs to `dist/`
- `bun run typecheck` → zero TS errors in both worker AND web
- `bun run test:api` → 20/20 tests pass (no regressions)
- `bun run gen:api-types` → full chain runs without a server in < 2s
